# GOLDEN DAYLIGHT CINEMA — build documentation

Everything in `GOLDEN_DAYLIGHT_CINEMA_PROJECT/` is generated by the scripts in
this folder. This file is the authoritative description of the pipeline: stages,
formulas, parameters, commands, runtimes and determinism.

```
build/
  gdc_colour.py      colour science: Apple Log 2, Apple Wide Gamut, Rec.709,
                     OKLab/OKLCh, smooth helpers, matrices, self-test
  gdc_grade.py       the look: tone curve, OKLab grade, gamut boundary +
                     compression, full pipeline, the BEFORE reference
  gdc_simulate.py    photos -> simulated Apple Log 2 (16-bit PNG + stats)
  gdc_bake.py        33³ least-squares bake (.cube writer/reader)
  lut_engine.py      independent .cube reader + trilinear/tetrahedral applier
  gdc_metrics.py     ΔE2000, ΔE-ITP, ROI helpers, OKLab summaries
  gdc_validate.py    every test in VALIDATION_REPORT.txt + charts
  gdc_render.py      BEFORE/AFTER preview renders from the delivered .cube
  gdc_gallery.py     GALLERY/ (HTML) + CONTACT_SHEET/ (JPEG)
  gdc_config.py      the eight scenes, their metadata and credit URLs
  pngio.py           8/16-bit PNG writer (numpy + zlib)
  dev_preview.py     quick contact-sheet previews for iteration
  requirements.txt   pinned dependencies
```

## 1. Run order

```bash
python -m venv .venv && .venv/bin/pip install -r build/requirements.txt   # once
cd GOLDEN_DAYLIGHT_CINEMA_PROJECT/build
../../.venv/bin/python gdc_colour.py            # self-test, no output files
../../.venv/bin/python gdc_simulate.py 1024     # simulated_log/*.png + stats
../../.venv/bin/python gdc_bake.py              # LUT/GOLDEN_DAYLIGHT_CINEMA.cube (~8 s)
../../.venv/bin/python gdc_render.py 1280       # PREVIEWS/*.png (~40 s)
../../.venv/bin/python gdc_validate.py          # validation/* (~50 s)
../../.venv/bin/python gdc_gallery.py           # GALLERY/ + CONTACT_SHEET/ (~6 s)
```

Total about two minutes on a laptop CPU. Nothing downloads anything at build
time; the photographs and the source metadata are already in the repository.

## 2. The pipeline, stage by stage

All stages run in float64 on arrays of shape `(…, 3)`; the code is vectorised
and has no per-pixel loops.

1. **Decode** — Apple Log 2 code → linear Apple Wide Gamut.
   `R >= 0.01: R = 2 ** ((code - 0.69336945) / 0.08550479) - 0.00964052`
   `R <  0.01: R = sqrt(max(code, 0) / 47.28711236) - 0.05641088`
   Negative results (code below video black 0.150476) are clamped to 0.
2. **Sanitise non-physical colours** — Apple Wide Gamut is much wider than
   Rec.709, so ~18 % of the *code cube* decodes to colours whose Rec.709
   luminance is negative. Such a colour is blended (smoothstep weight on
   `-Y / (0.02 * max(RGB))`) towards its positively-clipped version, so the
   transition at Y = 0 is C1 and impossible colours resolve to the nearest
   saturated colour instead of to black. Physics-valid colours are untouched.
3. **Tone map on luminance** — luminance `Y` drives a filmic curve; RGB keeps
   its chromaticity by scaling with `k = T / Ye`. `Ye` is a soft maximum of `Y`
   and `0.05 * max(RGB)` so that the curve stays well-defined at the toe.
   ```
   L = log2(Ye / 0.18)
   v = shoulder(1.16 * L - 0.115)        # rational shoulder, 2.46 stops, power 2.9
   T = 0.18 * 2 ** v,  then  T = min(T, 1.55 * Ye)   # shadow gain cap
   ```
4. **Grade in OKLab/OKLCh** — all of the following are smooth, overlapping
   kernels (circular Gaussians in hue, smoothstep in lightness):
   * midtone separation: `S` curve, amplitude 0.09
   * density: +10 % chroma at L = 0.56, width 0.30
   * highlight thinning: −10 % chroma from L = 0.86, ceiling 0.33
   * shadow thinning: −16 % chroma below L = 0.22
   * sky: −8.5 % chroma at 252°, hue +1.5° (towards deeper blue)
   * foliage: −6.5 % chroma at 141°, hue −3° (towards yellow)
   * stone/sand: +3 % chroma at 78°, hue +1.5°
   * warm split-tone: +0.0105 (a,b) at 71°, weighted to the upper midtones and
     to near-neutral pixels (0.062 → 0.22 chroma ramp), with a 55 % guard
     around the stone hue so warm walls do not go orange
   * cool split-tone: +0.0035 (a,b) at 258° in the shadows
   * skin protection: hue 50° ± 26°, chroma cap 0.105 (soft 0.03), plus a 28 %
     pull towards the 46° skin line
5. **Gamut compression** — exact in OKLCh: the maximum in-gamut chroma at
   (L, h) comes from a precomputed, hue-smoothed `GamutBoundary` (97 × 241 grid,
   first-exit search on a 85-step chroma ladder, σ = 3° hue / 1.5 L, 0.995
   margin). Chroma beyond `0.90 × Cmax` is compressed with an exponential knee,
   so nothing hard-clips and hue and lightness are preserved.
6. **Encode** — XYZ → linear Rec.709 → clip → `code = V ** (1/2.4)`.

The BEFORE reference is stages 1 → 6 without the tone map (identity), grade and
gamut compression: decode → AWG→Rec.709 matrix → clip → gamma 2.4.

## 3. How the table is baked

Naive sampling of a 33³ grid is noticeably wrong near video black, where the
Apple Log decode is a square root. Instead the 35,937 grid values per channel
are the solution of a linear least-squares problem:

```
minimise  0.04 · ||W_tri G − F||² + 0.64 · ||W_tet G − F||²
          + λ ||G − F_nodes||²  +  μ ||D₂ G||²

G       grid values (35,937 × 3)
F       analytic pipeline on 95,000 samples (uniform / near-black / neutral)
W_tri   trilinear interpolation weights, W_tet tetrahedral weights
λ = 3e-3   ridge towards the analytic node values
μ = 1.0    second-difference (smoothness) regulariser along each grid axis
```

The kernel weights favour tetrahedral (0.8² vs 0.2²) because that is what
Blackmagic Camera, Resolve and GPU implementations apply, while the small
trilinear term keeps the other mode honest. The normal equations are SPD and are
solved with Jacobi-preconditioned conjugate gradients (~17–30 iterations per
channel, residual ≈ 3e-4). The table is written with six decimals, red fastest.

Measured effect (VALIDATION_REPORT.txt §5): on the eight delivered frames the
fitted table is 19 % better than naive sampling in mean ΔE2000 and 28 % better at
p99 with tetrahedral interpolation; on the *whole* cube it wins on p99 and on
ΔE-ITP but is 4 % worse than naive in tetrahedral mean. That trade is reported,
not hidden.

## 4. Simulation of Apple Log 2 from the photographs

`gdc_simulate.py` treats each JPEG as scene light: sRGB → linear → Rec.709 →
Apple Wide Gamut → Apple Log 2, with a small white-balance/exposure trim per
scene so that the frame sits in a realistic log range (video black 0.150 to
about 0.70). The result is written as 16-bit PNG (`simulated_log/`) and is
labelled as simulated everywhere it appears: these are stills, not iPhone
recordings. `simulation_stats.json` records the code range and the round-trip
error of the simulation (≈ 8e-6).

## 5. Determinism

Every stage is deterministic float64 (seeded RNGs where randomness is used) and
independent of the machine's LUT conventions. `validation/render_hashes.json`
stores the SHA-256 of the LUT, of every simulated input frame and of every
BEFORE/AFTER float array, so a rebuild can be compared exactly.

## 6. Requirements

See `requirements.txt`. The pipeline needs numpy, scipy, Pillow, matplotlib and
colour-science 0.4.7 (the Apple Log constants and the ColorChecker data come from
it). Python 3.11 or newer.
