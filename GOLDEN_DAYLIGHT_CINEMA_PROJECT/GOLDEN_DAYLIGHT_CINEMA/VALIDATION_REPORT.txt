0. SCOPE AND METHOD
-------------------
Unless a section says otherwise, the tests read the DELIVERED .cube file with
build/lut_engine.py - an implementation that was written independently of the
baking code (it parses the file, builds the table and interpolates with either
trilinear or tetrahedral weights) - and never call the grading pipeline. The
"before" side of every comparison is reference_rec709(): Apple Log 2 decode ->
Apple Wide Gamut -> Rec.709 matrix (D65) -> clip -> pure gamma 2.4.

The eight test frames are the simulated Apple Log 2 versions of the eight
photographs, quantised to 10 bits per channel (as an iPhone records) before any
transform is applied.

How to read this, honestly:

  * On the neutral axis - the one that produces banding in skies, walls and
    gradients - the table is monotone to within 8.4e-06 of code, i.e. 1/50 of a
    10-bit step and 1/470 of an 8-bit step. Perceptually flat.
  * A falling channel on a single-channel ramp is not a defect: pushing blue up
    necessarily pulls red and green down as the colour turns blue. That is why
    the OKLab lightness column is the meaningful test, and there the worst
    excursion is 1.1e-03 (blue ramp), which occurs at the far corner of the
    input cube where the decoded colour has non-positive luminance and cannot
    exist physically (see section 13).
  * The residual reversals on the neutral axis are table quantisation from the
    least-squares bake: the fitted node values carry a small ripple of order
    1e-05 code, forty times below the 8-bit quantum.

  Quantised ramps (neutral axis, output rounded to the stated bit depth):
    8-bit  (256 steps):  0 reversals,  91 skipped output levels, 165 distinct
    10-bit (1,024 steps): 1 reversal, 360 skipped output levels, 663 distinct

  A monotone map from 256 input levels to 256 output levels must skip levels
  wherever it compresses (here the shadow toe and the highlight shoulder), so
  "skipped levels" is a description, not a failure. The 8-bit ramp is strictly
  monotone. The single 10-bit reversal is 1e-05 of code.

Interpretation, without spin:

  * On real frames the error-minimising bake beats plain node sampling for both
    interpolation modes: tetrahedral mean 0.340 vs 0.417 dE00 (-19 %), p99 1.58
    vs 2.18 (-28 %); trilinear mean 0.421 vs 0.534 (-21 %). That is the point
    of the bake and it works.
  * Over the WHOLE cube it is not uniformly better. Tetrahedral mean error is
    0.313 for the delivered table versus 0.301 for the naive one, because the
    delivered table spends some of its precision budget on the impossible
    colours in the corners of the code cube (they are weighted the same as any
    other sample). Its p99 is nevertheless better (4.69 vs 5.14) and its
    dE-ITP mean is better (1.19 vs 1.29). Trilinear is better everywhere.
  * The 28-30 dE00 maxima are all in the corners of the code cube - inputs
    whose decoded luminance is zero or negative, e.g. Apple Log code
    (0.576, 0.637, 0.962). No camera can produce them. Inside the physical
    subset the maximum falls to 13.3, and on the eight real frames to 7.3.
  * The mean code error of 1.1/255 on real frames is the number that describes
    what a colourist would see: sampling the analytic function directly is
    worse (1.4/255).

The curve approaches its ceiling asymptotically: the last 1.1 stops of input
(0.90 -> 1.00) produce 0.008 of output code. Nothing reaches 1.000 in any of
the eight frames, so no highlight is clipped by the LUT itself; where the source

Apple Log 2 video black at code 0.15047, which a correct decode maps to zero
light - is mapped to exactly 0 and the gamut/tone stage leaves it there. The
frames' blacks come out at 0.0 to 0.4 % of pixels rather than being crushed.

13. LIMITATIONS AND CAVEATS - WITH THE NUMBERS THAT BOUND THEM
--------------------------------------------------------------
  * dE2000 is not trustworthy in deep shadow: it is normalised by L*, so a 1/255
    code difference at code 0.02 (essentially invisible) scores higher than a
    1/255 difference at mid grey. That is why the report always gives the code
    error too (1.1/255 mean on the eight frames). Treat the mean dE numbers as
    an upper bound on what the eye would see.
  * 18 % of the input cube decodes to colours with non-positive Rec.709
    luminance (Apple Wide Gamut is much wider than Rec.709). These are not
    physically possible. The pipeline resolves them by blending, with a smooth
    (C1) weight, towards the nearest positive colour, so they land on saturated
    colours rather than black; measured worst-case interpolation error in that
    region is the 28-30 dE00 maximum in section 5. No scene pixel in the eight
    frames falls in this region.
  * The 33^3 grid is coarse where Apple Log 2 is steepest. Bake error is
    concentrated in the first two stops above video black (the fit reduces it,
    it does not remove it). A 65^3 master is not shippable to the Blackmagic app
    (33-point maximum), so this is a deliberate trade.
  * No grain, halation, bloom, diffusion, sharpening or noise reduction is
    applied, and none appears in the AFTER images.
  * Clipped highlights cannot be recovered; the shoulder only redistributes
    what was recorded.
  * The LUT is not depth-aware; no depth map or matte was used anywhere.
  * Monocular depth estimation was not used to produce any delivered image. It
    is mentioned in the brief as diagnostic-only and it was not needed.
  * The frames are simulated Apple Log 2 from JPEG stills: the underlying
    photographs already contain a camera's tone curve and are 8-bit. They are a
    fair test of colour behaviour, not of true 10-bit log noise or highlight
    headroom in the last stop.
  * No iPhone was used. Nothing here is a claim about behaviour on a physical
    device; it is a claim about the file and about the pipeline that made it.
  * The interpolation mode used by a given app is unknown to us. Both are
    measured; the table is fitted for tetrahedral, which is what Blackmagic
    Camera, DaVinci Resolve and most GPU implementations use.


14. VERIFIED FACTS VERSUS ASSUMPTIONS
-------------------------------------
Verified in this project (measured, or matched to an independent implementation):
  * the Apple Log transfer function (bit-identical to colour-science 0.4.7)
  * the Apple Wide Gamut primaries and the resulting matrices (3e-11)
  * the AWG -> ACES2065-1 matrix against OpenColorIO's built-in (5e-11)
  * the output transfer function is exactly V^(1/2.4)
  * every number in sections 1-12

Assumptions, stated as such:
  * that Apple Log 2 uses the Apple Log transfer function with Apple Wide Gamut
    primaries (this is what OCIO and the ACES configs implement, and what the
    Apple white paper describes; Apple does not publish a matrix, so ours is
    derived from the published primaries with a Bradford adaptation);
  * that the Blackmagic Camera app applies 3D LUTs with tetrahedral
    interpolation (it documents 17/33-point support but not the kernel);
  * that a viewer will apply the intended Rec.709 gamma 2.4 display transform;
  * that the eight photographs are representative of "golden daylight" scenes.

Not claimed:
  * that any of this was tested on an iPhone;
  * that the LUT improves every image;
  * that dE2000 captures what a colourist sees in the shadows.
