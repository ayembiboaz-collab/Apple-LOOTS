1. TECHNICAL SOURCES
--------------------------------------------------------------------------------

VERIFIED (official or cross-checked against two independent implementations):

  a) Apple Inc., "Apple Log 2 White Paper", September 2025
     (Part 028-00834, Version 1.1).
     - Transfer function = the Apple Log transfer function:
         P = gamma*log2(R + beta) + delta            for R >= Rt
         P = c*(R - R0)^2                            for R0 <= R < Rt
         P = 0                                       for R < R0
       with R0 = -0.05641088, Rt = 0.01, c = 47.28711236,
            beta = 0.00964052, gamma = 0.08550479, delta = 0.69336945,
            Pt = c*(Rt - R0)^2 = 0.20855531595464202.
     - Anchor table: 0% -> 0.150477 (10-bit 154), 18% -> 0.488272 (500),
       90% -> 0.681686 (697), 1200% -> 1.0 (1023).
     - Apple Wide Gamut chromaticities: R(0.725, 0.301), G(0.221, 0.814),
       B(0.068, -0.076), white D65 (0.3127, 0.3290).
     - Y'CbCr conversion per ITU-R BT.2020-2 (not used by this LUT).
     The white paper was reviewed from a copy distributed via the
     colour-science/colour GitHub repository (issue #1428 attachment,
     https://github.com/colour-science/colour/issues/1428); Apple distributes
     it through its developer resources.

  b) OpenColorIO (AcademySoftwareFoundation/OpenColorIO, main branch):
     - src/OpenColorIO/transforms/builtins/AppleCameras.cpp: identical
       transfer-function constants and Apple Wide Gamut chromaticities.
     - Built-in studio config (studio-config-v5.0.0_aces-v2.1_ocio-v2.6.ocio):
       "Linear Apple Wide Gamut" to_scene_reference matrix
         [0.694961049318096, 0.241405268785364, 0.06363368189654]
         [0.0473627464149326, 1.00429592505428, -0.0516586714692157]
         [-0.021989789359883, -0.0289891049714743, 1.05097889433136]
       used in this project as an independent cross-check (see test 3.2).

  c) ITU-R BT.709-6 (Rec.709 primaries R(0.640,0.330) G(0.300,0.600)
     B(0.150,0.060), D65) and ITU-R BT.1886 (reference EOTF; the pure
     gamma-2.4 power law is used as the output encoding).

ASSUMED (documented, not official):

  - The "neutral technical conversion" used for the BEFORE images is
    Apple Log 2 decode -> Apple Wide Gamut to Rec.709 -> pure gamma 2.4,
    with no tone mapping and no grade. Apple's own Log-to-709 conversion LUTs
    are distributed only through login-gated developer/Final Cut downloads and
    could not be retrieved from this environment, so this transparent
    conversion was used as the reference baseline instead.
  - The simulation of Apple Log 2 footage from stills treats sRGB-decoded
    linear light as a scene-linear Rec.709 proxy (system gamma 1.0). See
    section 5.
  - Gamma 2.4 output is interpreted as code = display_light^(1/2.4) (the
    inverse of the BT.1886 power law), which is the convention for
    display-referred Rec.709 gamma 2.4 deliverables.

2. WHAT THE LUT DOES (exact pipeline, see scripts/gdc_core.py)
--------------------------------------------------------------------------------

  1. Apple Log 2 transfer-function decode (constants above) -> scene-linear
     RGB in Apple Wide Gamut (D65).
  2. 3x3 gamut transform Apple Wide Gamut -> Rec.709 (D65, no chromatic
     adaptation required).
  3. GOLDEN DAYLIGHT CINEMA grade:
     a. Filmic tone curve (monotone PCHIP through stop-anchored knots,
        18% grey -> code 0.42; deep detailed shadows; long smooth shoulder;
        nothing at or above mid grey is rendered brighter than the neutral
        conversion; designed film black floor at code 0.012).
     b. Saturation curve (rich midtones, protected whites/blacks) with
        vibrance damping for already-saturated colours.
     c. Hue-aware colour work: sky enrichment with cyan control and cloud
        protection; foliage saturation control and green-ward hue correction;
        skin protection (no orange/yellow drift); warm-highlight recovery for
        sunlit skin.
     d. Golden warmth: amber gains weighted by luminance (sunlit mids) and
        saturation (neutrals/whites barely move), attenuated on already-warm
        (golden-hour) content and on sky hues.
     e. Subtle cool split-tone in deep desaturated shadows (max ~1.3/255
        channel deviation) for sun/shade separation.
  4. Rec.709 gamma 2.4 encode (code = light^(1/2.4)), clamped to [0,1].

  The .cube was produced by evaluating this pipeline at every node of a
  33 x 33 x 33 grid spanning input code values [0,1] (Adobe/Iridas .cube
  line order, R varying fastest).

3. TESTS PERFORMED ON THE DELIVERED .CUBE
--------------------------------------------------------------------------------
(Run: python3 scripts/validate_lut.py - all 29 checks pass.)

3.1 Structure, syntax, numerical integrity
  - Parses as a valid .cube; TITLE "GOLDEN DAYLIGHT CINEMA"; LUT_3D_SIZE 33.
  - Exactly 33^3 = 35,937 data lines, three numeric values each.
  - All values finite (no NaN, no +/-Inf) and within [0,1]
    (observed range [0.000000, 0.952874]).
  - Tetrahedral interpolation over the full input domain stays finite and
    within [0,1].

3.2 Apple Log 2 decoding and Apple Wide Gamut transformation
  - The implementation reproduces the white-paper anchor table exactly:
    0% -> 0.150477, 18% -> 0.488272, 90% -> 0.681686, and code 1.0 decodes to
    12.000002 (1200% of reference white; the 2e-6 residual comes from Apple's
    constants being published to 8 decimals).
  - Encode/decode roundtrips are exact to < 1e-9 above the white paper's R0.
  - The Apple Wide Gamut -> ACES2065-1 (AP0) matrix derived in this project
    (primaries + Bradford adaptation) matches the matrix published in
    OpenColorIO's built-in studio config to 3.55e-15 - i.e. the gamut
    mathematics are verified against a second, independent implementation.
  - Saturated Apple Wide Gamut primary inputs render finite and in range.

3.3 Rec.709 gamma 2.4 output
  - Output encoding is code = display_light^(1/2.4) throughout (verified by
    construction and by the 18% grey placement: scene 0.18 -> display light
    0.1331 -> code 0.42, consistent with the inverse BT.1886 power law).
  - 1200% scene white (input code 1.0) renders at code 0.9094 - the
    highlight shoulder deliberately keeps speculars below clipping.

3.4 Neutral behaviour, clipping, smoothness
  - Grey axis (R=G=B input) stays grey: channel deviation is exactly zero
    above the deep-shadow zone and at most 1.311/255 inside it (the designed
    cool split-tone).
  - Whites/highlights are exactly neutral (within float epsilon, < 1e-12).
  - Grey-axis luminance is monotonically increasing (no tone reversal).
  - No black crush: sensor black (code 0.150477) renders at a designed film
    floor of 9.0/255; -5 stops renders at 33/255 (detailed shadows).
  - No banding: second derivative of the cube output along smooth synthetic
    sky/skin/stone/foliage gradients is <= 0.141/255.
  - Cube matches the authoring pipeline to 0.46/255 on the grey axis above
    scene 0.4%; in the steep log toe the interpolation error is at most
    6.07/255, concentrated at sensor black (documented 33^3 limitation).

4. LOOK-DEVELOPMENT MEASUREMENTS (eight scenes, BEFORE vs AFTER)
--------------------------------------------------------------------------------
Measured on the delivered files (1280x720 PNG renders; regions defined by
hue/saturation masks per image):

  - Mean display luma change: -14% to -23% depending on scene (the LUT never
    brightens footage; the brightest beach scene is compressed most).
  - Sky regions: saturation +5 to +11% on average, value -11% (slightly
    deeper), hue held toward blue (no cyan/turquoise drift; cloud whites
    measurably cleaner).
  - Foliage regions: saturation -8 to -20% (controlled), value ~unchanged,
    hue pulled away from yellow-green toward green.
  - Skin regions: saturation ~unchanged (+/-5%), hue within +/-1.5 deg,
    subtle warm shift; sunlit highlights roll off warm ("creamy") instead of
    clipping.
  - Whites (clouds, shirts, sand): no yellow cast - the R-B balance of the
    white regions is unchanged or very slightly reduced.
  - Shadow regions: deepened with detail retained (p1 luma >= 0.036 across
    scenes; < 0.1% of pixels at absolute black), slight blue separation.
  - Clipping: 0.00% of pixels reach 255 in any AFTER render.

5. WHAT WAS SIMULATED
--------------------------------------------------------------------------------
No genuine Apple Log 2 camera footage was available in this environment. All
test "footage" is SIMULATED Apple Log 2, produced as follows
(scripts/gdc_core.py : simulate_apple_log2):

  1. Eight photorealistic scene stills were AI-generated (Arena image
     generation) for this project - they are NOT iPhone photographs and are
     NOT representative of iPhone 17 Pro sensor characteristics (noise,
     real spectral response, real dynamic range). Sources and credits:
     sources/SOURCES_AND_CREDITS.md.
  2. Each still was sRGB-decoded to linear light and treated as a scene-linear
     Rec.709 proxy of the scene (system gamma 1.0 assumption).
  3. Converted to Apple Wide Gamut primaries (verified matrix) and encoded
     with the official Apple Log 2 transfer function.
  4. Quantised to 10-bit full range, matching ProRes container precision.

  Consequences (important):
  - Because the stills are SDR (display-referred), the simulated scene-linear
    signal tops out near +2.5 stops over 18% grey. Real Log 2 captures carry
    far more highlight headroom. The LUT's behaviour above that range was
    therefore validated numerically (synthetic exposure sweeps, swatch tests
    to +4 EV, tone-curve checks to 1200% scene reflectance), not
    photographically.
  - The AI stills already contain processed, pleasing colour; they are not
    raw sensor data. The BEFORE/AFTER comparisons therefore show the LUT's
    transformation of that content, not of a real camera signal.
  - "BEFORE" = neutral technical conversion (Apple Log 2 decode -> AWG to
    Rec.709 -> gamma 2.4, no tone mapping, no grade) of the same simulated
    footage; "AFTER" = the delivered .cube. Same source, same simulated
    exposure, same processing except the LUT.

6. WHAT WAS NOT TESTED (do not assume otherwise)
--------------------------------------------------------------------------------
  - No physical iPhone, no Blackmagic Camera app, no DaVinci Resolve, no
    Final Cut Pro, and no hardware LUT box were used in this project. All
    rendering and measurement happened in this project's Python pipeline
    (numpy; verified against OpenColorIO's published matrices).
  - The LUT has not been applied to real iPhone 17 Pro Apple Log 2 footage.
  - The Blackmagic Camera import instructions in README.txt follow the app's
    documented custom LUT support but were not exercised on a device.
  - The HTML gallery was tested by serving it over HTTP and checking
    resources/status codes from this environment; it was NOT opened on an
    iPhone or in iPhone Safari. No physical mobile testing of any kind was
    performed.
  - Display fidelity: preview PNGs store Rec.709 gamma 2.4 code values
    directly; on a typical sRGB/gamma-2.2 browser display they will appear
    very slightly darker than on a reference 2.4 display. This is expected.

7. KNOWN TRADE-OFFS
--------------------------------------------------------------------------------
  - A LUT cannot recover clipped highlights. If the camera clipped the sky,
    no detail returns; the shoulder will simply render the clipped area as a
    smooth, slightly warm top-end.
  - Overall level: the grade renders midtones richer and somewhat darker than
    a flat log conversion (18% grey at code 0.42; mean luma -14 to -23% on
    the test scenes). This is the intended "luxury film" density; exposure
    can be trimmed before the LUT if a brighter base is wanted.
  - 33^3 grid: the steep log toe is smoothed by grid interpolation; sensor
    black renders at a designed film floor (~9/255) rather than absolute 0,
    and the deepest ~1/3-stop below scene 0.4% deviates from the authoring
    curve by up to ~6/255. Above that region the cube matches the authoring
    pipeline to 0.46/255.
  - The cool shadow split-tone (max 1.3/255 channel deviation) means the
    grey axis is not perfectly neutral in the deepest shadows - intentional,
    for sun/shade dimensionality.
  - Saturated deep blues (e.g. dark glass reflecting sky) gain noticeably
    more saturation than average content (up to ~+25-35% on the architecture
    test scene). This reads as depth on reflective glass but is the most
    aggressive behaviour of the look.
  - Warmth is attenuated on strongly orange/yellow content so golden-hour
    footage is not over-warmed; heavily saturated golden scenes therefore
    receive less additional warmth than neutral midday scenes.
